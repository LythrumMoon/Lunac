# 模组冲突处置

**铁律：唯一提供者优先于排序。** 两个包争同一份资源时，最稳的做法是停用其中一个（改名，不删除）；排序只是让它们共存时的退路。

## 1. 先建冲突清单

- 逐条列出「共享路径 → 提供者列表」，不要只数冲突条数。
- 区分三类：真正互斥的替换件、设计上就该叠加的补丁、纯噪音（共享通用模板）。
- 只有第一类需要裁决；后两类动排序只会引入风险。

## 2. 唯一提供者

- 切换同类替换件时，**先停用旧同类**（改名保留），再启用新件。
- 停用后重跑一次清单，确认该路径只剩一个提供者。
- 停用理由必须写清楚；理由站不住时（例如路径在原版里根本不存在）要撤回停用。

## 3. 排序只在必须共存时用

- 加载语义必须取**一手来源**：加载器自己的日志、可执行文件里的字符串、配置解析输出。不要拿文件名前缀猜。
- 先写「工具界面顺序 ↔ 磁盘文件顺序」的映射（例如「面板最上 = 文件最后一行」），并用一次计数或日志验证；映射没验证不准动手。
- 框架/依赖类先加载（弱，允许被覆盖）；内容/替换件后加载（强）；补丁最后。
- 调整前备份，调整后用「谁提供该路径」清单对比赢家是否变化；赢家变了要说明原因。

## 4. 写文件前

- 检查目标目录是否有程序正在运行、是否持有文件锁；有就先请用户关闭，再写。
- 实验产物、二分副本、备份只放在任务临时目录（`temp\transStorage\<task>\`），不要写进被操作的目录。
- 配置类文件按目标程序的要求选编码：需要无 BOM 的（如 tweak）一律无 BOM；`.cmd` / `.bat` 只写纯 ASCII，逻辑放 `.mjs` / `.ps1`。
- 任何「已生效 / 已修复」必须由目标程序日志或文件系统状态背书，脚本自己的 echo 不算。

## 5. 红旗

- 想靠改名前缀（`!`、`zzz_`）解决一切冲突。
- 连续几轮调顺序没有效果，却还在调顺序。
- 改完不验证赢家、只凭「应该好了」下结论。
- 在加载器/排序器还开着的时候写它托管的清单。
