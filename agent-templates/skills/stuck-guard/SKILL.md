# 命令卡住自检（stuck-guard）

**铁律：别让自己被一条命令无期限地挂住。** 你（模型）在工具调用返回前是**瞎子** —— 既看不到输出也不会自己去检查。所以「卡住」这件事只能靠**事前预防** + **事后诊断**两半来解决，没有「一边阻塞一边自检」这回事。

## 一、事前预防（最重要）

任何**可能长时间运行或可能不退出**的命令，都不要用「前台无限等」的形态发出去：

| 形态 | 怎么做 | 什么时候 |
|---|---|---|
| 常驻服务 / 服务器（ComfyUI、web server、watcher） | **后台运行**：用 `Start-Process` 且**不让它继承管道**（`-WindowStyle Hidden`；不要 `cmd /c start /b`、不要 `Start-Job`） | 你只负责「启动它」，随后单独探测端口 / 日志确认就绪 |
| 编译 / 训练 / 大批处理（会跑很久但有明确终点） | 给 **`timeout`**（毫秒），或直接转后台，别用默认值硬等 | 预计 > 1 分钟 |
| 不确定会不会退出的东西 | 一律先给一个**你能接受的 timeout**（例：`timeout: 60000`），让它把控制权还给你，再决定下一步 |

**判据**：一条命令如果「不知道它什么时候结束」，就不该前台等它。

## 二、事后诊断：它在干活，还是挂了？

怀疑卡住时，**至少取两条**下列证据（一条不够 —— 编译时可能长时间「无输出」但确实在算）：

1. **实时输出还在长**吗？看那张命令卡是否还在追加文本；长输出落盘在 `<Lunac 根>\temp\tool-outputs\`。
2. **相关进程的 CPU 在涨**吗？采两次（间隔 2 秒）比较 CPU 秒数：
   ```powershell
   1..2 | ForEach-Object { (Get-Process -Id <pid>).CPU; Start-Sleep -Seconds 2 }
   ```
3. **它的子进程还在吗**？（编译会有 `cc1` / `rustc` / `link`；训练会有 `python`）
   ```powershell
   Get-CimInstance Win32_Process -Filter "ParentProcessId=<pid>" | Select-Object ProcessId,Name,CommandLine
   ```
4. **预期产物 / 端口 / 日志在动**吗？（目标文件 mtime、`Test-NetConnection`、目标日志的尾行时间戳）

## 三、处置

- **在干活**（编译中 / 输出还在长 / CPU 在涨 / 子进程健在）⇒ **让它继续跑**。别中止。转后台（用户点「后台运行」，或你下次改用后台形态）然后把这一轮用来做别的事。
- **确实挂了**（无输出 + 两次采样 CPU 不动 + 没有预期子进程 + 产物 / 端口不动）⇒ **中止**：
  - 是**你自己起的**进程：`taskkill /F /T /PID <pid>`（`/T` 连子进程一起）。
  - 是**当前正在阻塞的那条命令**：你没法自己取消它（你正卡在里面）—— 告诉用户「请点那张卡上的『停止』」，并说明你打算改用什么形态重来。
- **常驻服务**（ComfyUI 之类）本来就该长跑：你前台等它 = 自己把自己挂住。它「启动完」的判据是**端口就绪 / 日志打出 ready**，不是「命令返回」。

## 四、核对日志（每次都要）

```powershell
# 同一次 agent 运行的日志（看清它最后一步在干什么、有没有转后台 / 超时 / 停止）
Get-Content "<Lunac 根>\temp\logs\agent-<YYYY-MM-DD>.log" -Tail 40
# 被截断的长输出全文
Get-ChildItem "<Lunac 根>\temp\tool-outputs" -File | Sort-Object LastWriteTime -Descending | Select-Object -First 5
```

日志里几条关键行：`shell[...] exit=… timeout=… stopped=…`、`tool_control: 命令 … 转后台 / 停止`、`已转后台 id=…`。**没有** `exit=` 行就说明命令还没收口。

## 五、已知坑（别踩）

- **detached 常驻进程会继承父命令的输出管道** ⇒ 父命令「其实已经退出了」，但工具调用还在等管道 EOF，看起来像卡死。**启动常驻进程时别让它继承管道**（见第一节），否则连「转后台 / 停止」都可能没有落点。
- **`timeout` 不是万能的**：它只在被等的进程还活着时生效。进程已经退出、只是管道没关的那一形态，靠的是上游的宽限期收口（已被修）。
- **别用「再等一会儿」当诊断**：连着两次都在同一个地方干等，就该按第二节取证据了。

## 六、回报格式

```
现象：<哪条命令、跑了多久、有没有输出>
判据：<实时输出 / CPU 两次采样 / 子进程 / 产物，各一句>
结论：在干活 / 已卡死
处置：<让它继续（转后台） / taskkill <pid> / 请用户点停止>
日志：<相关日志行原文>
```
